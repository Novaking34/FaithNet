== Leaving the Laboratory: Four Real Devices, Zero Simulation

Before Wave 9 touched real Wi-Fi silicon, FaithNet already had a pristine
laboratory record:

* **46 dedicated 5-Block test files** across the 4x4 Matrix (`Functional`,
  `Unit`, `Integrated`, `System`) passing with `-race` and zero data races.
* **22/22 live Block 4 pre-flight gates** passing inside `faithnet-node --audit`.
* **5 local OS playtester harnesses** proving cross-process UDP/TCP, chaos
  packet corruption, silent blackhole auto-cascade, kernel FIFO SLIP serial,
  `+3.93 dB` SNR acoustic AFSK with leading mic silence, and `6,126 req/s` Well
  load under `120/120` blocked attacks.

Then we stepped into physical reality with **Field Kit 01** across four real
consumer devices on real RF spectrum:

1. **Laptop #1 (Home Anchor & Micro-ISP):** `professorseanex-Inspiron-16-5640`
   (Ubuntu Linux `7.0.0-43-generic`, Realtek `RTL8852CE` Wi-Fi 6E chip running
   the kernel `rtw89` driver).
2. **Laptop #2 (Peer & Visitor):** `seanje-lenox-wise-Inspiron-5579` (Ubuntu
   Linux, standard browser + `curl`, zero Go toolchain installed).
3. **Mobile Client:** Consumer iOS iPhone (Safari + iOS Trust Store).
4. **Unexpected Stress Device:** Sony PlayStation console joining
   `FaithNet-HomeRoom` and streaming live YouTube through our userspace NAT!

The moment real consumer browsers, operating systems, RFC standards, and Wi-Fi
radio firmware interacted with FaithNet in real time, **six brand-new physical
edge cases surfaced immediately** — not because the lab tests failed, but
precisely because **no single unit test contains Firefox's HTTPS-Only heuristics,
Apple's RFC 6762 mDNS resolver, NetworkManager's D-Bus state machine, and
Realtek's single-channel firmware lock running simultaneously.**

== Understanding Game-Systems Edge Cases (Bugs Between Moving Parts)

In game engine engineering (and sovereign OS/network design), the hardest bugs
rarely live *inside* one isolated function. Every individual subsystem can pass
100% of its unit tests and still collide when five independent state machines
move at the same time:

* **System A** (`hostapd`) is healthy and legitimately holding `ap0` on 2.4 GHz
  Channel 11.
* **System B** (`NetworkManager`) is healthy and legitimately trying to roam
  `wlp3s0` onto a phone hotspot on a different channel.
* **System C** (`rtw89` kernel driver + `RTL8852CE` silicon) is faithfully
  enforcing its hardware physics limit (`#channels <= 1`).
* **System D** (`systemd`) is booting user-space `faithnet-home.service` while
  an ephemeral foreground terminal script died with the reboot.
* **System E** (a human user) simply clicks a phone hotspot in the system tray
  and reboots expecting paired devices to rejoin automatically.

**None of Systems A–E had a "syntax error."** Yet their live temporal
intersection created a PCI radio lockup and a silent post-reboot disconnect.
Watching that unfold in real time taught a lesson that synthetic mocks can never
simulate: **an edge case is a collision of valid assumptions across system
boundaries.**

== Why Deep Layered Testing Accelerated Every Single Fix

A tempting mistake after seeing live hardware bugs is to wonder whether the
4x4 Lab Matrix was "wasted effort." **Field Kit 01 proved the exact opposite.**

Every time a live failure occurred in Sessions 003–006, our diagnosis time was
**under 60 seconds** *because* the 4x4 Matrix had already mathematically proven
the lower layers:

* When `faithnet.local` timed out on iPhone (Gap #5), we *immediately* knew
  the Go HTTP server, TLS handshake, and DHCP lease were 100% healthy — because
  `https://10.77.77.1:8077/` showed a green padlock. That instantly isolated the
  bug to OS DNS resolution (RFC 6762).
* When `hello` appeared twice on The Well (Gap #7), we *immediately* knew
  Layer 0/1 codec and Layer 2 router weren't corrupting sequence IDs — because
  both frames had identical `seq=2`, pointing straight to `UDPTransceiver.Send`.
* When switching to a phone hotspot dropped `wlp3s0` (Gap #8), we *immediately*
  knew Go `faithnet-home.service` was blameless — isolating the exact conflict
  between `hostapd` channel lock and `rtw89` single-channel silicon.

**Layered testing does not prevent real-world edge cases — it turns multi-day
mystery crashes into 60-second surgical diagnoses.**

== Cross-Platform Field Kit Parity (Wave 14)

Field Kit 01 began on Ubuntu Linux, where kernel `nl80211` allows true
simultaneous `STA + AP` on a single Realtek card. Wave 14 audited the entire Go
codebase and expanded Field Kit 01 to **Linux, Windows (PowerShell), and macOS**
with complete Rev 5 5-Block symmetry:

1. **Go Core Cross-Compilation Verified (`0` changes needed in Layers 0–3A):**
   `GOOS=windows GOARCH=amd64`, `GOOS=darwin GOARCH=arm64`, and
   `GOOS=darwin GOARCH=amd64` all compiled cleanly on the very first pass.
2. **One Real Code Upgrade Found by Audit (`GET /pair.ps1`):**
   The Well (`interpreter/captive_web.go`) previously only generated POSIX
   `GET /pair.sh`. Wave 14 added native **`GET /pair.ps1`** and OS-aware card
   rendering (`irm http://<host>/pair.ps1 | iex` for Windows browsers;
   `curl -fsSL http://<host>/pair.sh | sh` for Linux/macOS).
3. **Live PowerShell 7.7.0 Parity Verification:**
   All 3 Windows `.ps1` Field Kit scripts were executed live via
   `/snap/bin/pwsh -NoProfile -File ... -AuditOnly`, verifying real PowerShell
   syntax, Block 4 pre-flight diagnostics, and zero-mutation safety guards.
4. **Honest OS Radio Reality Documented Upfront:**
   * **Linux (`nl80211`):** Full single-radio simultaneous `STA + AP` via
     `hostapd` + `dnsmasq` + `faithnet-ap.service` (**verified live**).
   * **Windows (`WinRT` / `netsh`):** Modern Wi-Fi Direct **Mobile Hotspot**
     supports single-radio STA+AP sharing cleanly through Windows Settings /
     WinRT (`NetworkOperatorTetheringManager`), while legacy `netsh wlan
     set hostednetwork` is deprecated on Windows 10/11 drivers.
   * **macOS (`CoreWLAN` / `InternetSharing`):** Apple's built-in Wi-Fi driver
     blocks simultaneous STA+AP on a single Wi-Fi interface; sharing upstream
     internet over macOS Wi-Fi AP requires Ethernet/USB/tethered upstream plus
     Wi-Fi AP, or running `faithnet-node` directly on the shared LAN.
